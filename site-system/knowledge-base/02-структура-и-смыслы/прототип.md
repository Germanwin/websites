# Прототип

**Прототип** — чёрно-белый макет сайта со всеми смыслами и текстами.
Иногда его называют техническим заданием.

## Зачем он нужен

1. **ТЗ для дизайнера.** Внятное ТЗ = выше скорость и меньше правок
2. **Дешёвые изменения смыслов.** Переписать смыслы в чёрно-белом прототипе — минуты.
   Переделывать их после дизайна — «реальное болото»
3. **Наглядность гипотез** до дорогой реализации
4. **Конверсия.** Смыслы прорабатываются полностью и осознанно, а не «как получилось»
5. **Рост чека.** Прототип — отдельная услуга, а мобильная версия прототипа даёт
   ещё +30% к стоимости

## Порядок работы

```
Бриф + анализ ЦА и конкурентов
        ↓
Смысловая карта (боли / потребности / страхи / критерии / факты)
        ↓
Оффер по одной из 8 формул
        ↓
Структура блоков под критерии выбора этого сегмента
        ↓
Прототип ПК (чёрно-белый, со всеми текстами)   ← утверждаем у клиента
        ↓
Прототип мобильной версии (10–12 блоков)       ← утверждаем отдельно
        ↓
Дизайн  →  Вёрстка / сборка  →  Аналитика и цели  →  Трафик  →  A/B-тесты
```

⚠️ **Никогда не презентуй ПК и мобильную версию одновременно** — получишь вдвое
больше правок.

## Что должно быть в прототипе каждого блока

- Заголовок блока (по правилам копирайтинга, не «О компании»)
- Основной текст / буллиты — **финальный**, а не «рыба»
- Пометка, какая картинка нужна и что на ней изображено
- Тексты кнопок
- Комментарии дизайнеру: акценты, что выделить, что должно быть крупным

## Правило пикселя

> У каждого пикселя есть конкретная бизнес-задача. Он либо пустой — чтобы не
> отвлекать внимание, — либо является смысловым элементом.

Проверяй каждый блок: какую задачу он решает? Какое возражение снимает?
Какой критерий выбора закрывает? Если ответа нет — блок лишний.

## Инструменты

- **Figma** — стандарт. Прототип, дизайн, передача разработке
- **Тильда / Flexbe** — если собираешь сразу в конструкторе
- Для черновика годится хоть Google Docs — важны смыслы, а не инструмент
